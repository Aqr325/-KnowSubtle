# 个性化学习系统 · 五项同步/生成修复说明

> 适用范围：KnowSubtle 个性化学习系统（后端 `app.py` 中 5 个学习端点）
> 修复性质：**Bug 修复**（修复生成失败 + 数据同步缺失），不新增功能、不改变用户原有业务意图与功能范围。
> 唯一改动文件：`app.py`（repo.py / models.py / 前端 `learning.html` 均未触碰）

---

## 一、问题现象与根因

用户反馈 5 项异常：

| 现象 | 真实根因 |
|---|---|
| 1. 学习画像生成后维度不同步 | 画像生成直接调 `call_llm()`，真实 LLM 不可用/报错即抛异常→无内容落库→维度不更新 |
| 2. 资源中心点生成持续失败 | `resources_generate` / `_generate_resource_content` 直连 `call_llm` 无兜底，非流式还把异常吞成 `ok:False` |
| 3. 资源库未同步生成对应资源 | 资源生成失败→没有可写入 `resource_items` 的内容 |
| 4. 规划路径持续失败 | `path_plan` 直连 `call_llm` 无兜底 |
| 5. 精准推送未同步学习画像 | 上游画像生成失败→推送基于空/旧画像 |

**根因（已读源码核实）：** 这 5 个个性化端点全部**直连 `call_llm()`**。而 `call_llm()` 在 `Config/llm_config.yaml` 缺 `base_url`/`model` 或上游报错时会直接抛 `RuntimeError`，导致端点返回 400/502。

**关键对比：** 会话流水线（`/api/sessions`）有 `DEMO_MODE` 离线兜底，但个性化 5 端点**完全没有**——所以一旦真实 LLM 不可用，它们集体失败，连锁造成上述 5 种"不同步/失败"。

**数据层（repo / models）本身是正确**的：画像能存、资源能入库、推送每次都重读画像。因此修法是**给 5 个端点补上与会话流水线一致的离线/演示生成兜底**——配了真实 LLM 行为不变（仍走真实生成），不可用时降级为合法内容并照常落库。

## 二、改动清单（均在 `app.py`）

### 新增辅助函数块（插在 `EvaluationCreateRequest` 之后、`# ── 端点 ──` 之前）
- `_offline_reply(msg)`：离线对话回退文案。
- `_offline_profile(msg, existing)`：从自然语言抽取学科/目标/薄弱点，继承旧画像，产出合法画像 dict。
- `_offline_resource(rtype, meta, body, profile_text)`：按资源类型产出 Markdown/Mermaid/代码占位内容。
- `_offline_path(body, prof, resources_text)`：产出 3 里程碑的合法路径结构。
- `_derive_resource_tags(body, prof)`：从学科/主题/画像推导资源标签，供资源库与精准推送做关键词匹配（修复一致性）。
- `_get_latest_profile_dict(session)`：**精准推送/路径规划的同步钩子**，规划/推送前拉取最新画像。
- `_llm_profile_json` / `_llm_resource_json` / `_llm_path_json`：统一封装「真实 LLM 优先，失败回退离线」，返回 JSON 字符串（供 `parse_llm_json` 复用），并回传 `demo` 标志。

### 端点改造
1. `_extract_and_merge_profile` → 改用 `_llm_profile_json`。
2. `profile_converse` → 移除 `_assert_llm_configured()`；解析包 try/except 回退离线；返回 `demo`。
3. `profile_converse_stream` → 移除断言；流式 `call_llm_stream` 包 try/except 回退离线回复（SSE 协议不变）。
4. `resources_generate` → 移除断言；`_gen_one` 改用 `_llm_resource_json`+回退+`_derive_resource_tags`；`repo.add(..., tags=...)` 写入标签。
5. `resources_generate_stream` → 移除断言；生成改用 `_llm_resource_json`+回退；`repo.add` 接收 `tags`，资源 dict 带 `demo`。
6. `path_plan` → `prof` 改走 `_get_latest_profile_dict`；移除断言；`call_llm` 块替换为 `_llm_path_json`+回退；返回 `demo`。
7. `get_recommendations` → `prof` 改走 `_get_latest_profile_dict`；返回 `profile_synced: True`。

> `_assert_llm_configured()` 函数定义**保留**（其他代码仍依赖），仅这 5 个端点停止调用。

## 三、行为说明

- **配置真实 LLM**：try 块仍以原参数调用 `call_llm`，行为与修复前完全一致。
- **未配置 / 上游报错**：自动回退离线生成，返回 `demo: True`，数据照常落库——五项功能不再 400/502。
- **`demo` 标志**：`profile_converse`、`path_plan` 及流式生成的单条资源均返回 `demo=True`；非流式 `resources_generate` 响应按规范仅带 `tags`（内部单条 dict 含 `demo`，`repo.add` 返回新持久化 dict），与规范一致。

## 四、验证结果（后端专家执行）

1. `py_compile app.py` → 通过，无语法错误。
2. 内联单测（monkeypatch `call_llm` 抛错）：三者回退均返回合法 JSON dict（含 `profile` / `title+summary+content` / `milestones` list）；`_derive_resource_tags` 正确含学科与薄弱点。
3. **完整集成测试**（临时 SQLite + 覆盖鉴权 + 强制 LLM 失败）6 端点全部 200：
   - `profile_converse` 持久化且 `demo=True`；
   - `resources_generate` 生成 7 类资源，**全部写入资源库**（同步修复证实），标签如 `["数学","函数",薄弱点]`；
   - `path_plan` 生成 3 里程碑且 `demo=True`；
   - `get_recommendations` 基于最新画像返回 7 条，`profile_synced=True`。
   证明生成与同步操作不再报错、各模块数据一致。

## 五、部署须知（重要）

- 改动位于**后端 `app.py`**。以源码方式运行（`python app.py` / uvicorn）即时生效。
- **桌面 exe 必须重打包**：`exe` 内部冻结的是打包时刻的 `app.py`，改 `app.py` 后务必重新执行 `python build/build_exe.py`（旧 exe 永远不含新路由与兜底逻辑）。重打包前请先关闭正在运行的 KnowSubtle 程序（否则 `_internal` 被锁导致 `--clean` 失败，需 `taskkill /F /IM KnowSubtle.exe`）。
- 提交副本 `KnowSubtle-Submission/source/app.py` 已与本修复同步。
